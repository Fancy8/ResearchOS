# 研发流程与迭代工单

企业级流程围绕明确职责、可追踪交付和质量门禁组织；本文件为研发计划，不表示已创建外部工单或已批准发布。

## 阶段、责任与交付门禁

```mermaid
flowchart LR
    accTitle: ResearchOS delivery gates
    accDescr: Product and technical reviews establish the baseline. Ready stories enter implementation and review, then acceptance, release rehearsal and controlled pilot. Pilot evidence feeds the next iteration.
    kickoff["立项与用户验证"] --> scope["需求基线 / G1"]
    scope --> design["架构与设计 / G2"]
    design --> ready["工单就绪 / DoR"]
    ready --> build["开发 / Review / CI"]
    build --> accept["集成验收 / G3"]
    accept --> rehearse["恢复与发布演练 / G4"]
    rehearse --> pilot["受控试用 / G5"]
    pilot --> learn["指标与反馈复盘"]
    learn --> scope
```

文本说明：每轮需求冻结后完成技术设计和就绪检查，再开发、代码审查、集成验收、恢复/发布演练；达标进入试用，真实使用反馈形成下一轮需求。门禁不通过的项目回到相应阶段补齐证据。

| 阶段 | 负责人/协作 | 可审查产物 | 退出条件 |
| --- | --- | --- | --- |
| 立项 | 项目负责人/PM | 产品问题、用户、范围、资源与预算假设 | 目标和人员明确，试用渠道存在 |
| G1 需求评审 | PM/UX/QA/TL | PRD、追踪矩阵、验收、优先级、变更记录 | F01–F15 和非目标无歧义 |
| G2 技术/设计评审 | TL/FE/BE/QA | 线框、ADR、模型、API、PDF/并发 spike、威胁模型 | 关键风险有验证结果、依赖明确 |
| 迭代开发 | FE/BE/QA | 小工单、PR、自动化测试、可演示集成环境 | 每工单 DoD 通过 |
| G3 联调验收 | QA/PM | AC/TC/DB 报告、E2E 录像、性能和兼容结果 | P0 完整，阻断和高严重缺陷为零 |
| G4 发布评审 | TL/运维/QA | 备份恢复、迁移演练、运行手册、回滚材料 | 可恢复、可监控、有值班责任 |
| G5 试用决策 | PM/项目负责人 | 灰度记录、已知问题、试用授权与指标口径 | 批准具体版本进入受控试用 |

小团队一人可兼多个角色，但重要数据/权限变更至少有独立审查者。技术负责人对架构一致性负责；PM 决定产品取舍；QA 提供客观验收证据；发布责任人核准具体镜像和迁移，不用口头“差不多完成”代替记录。

## 工单就绪与完成定义

Definition of Ready：工单有用户价值、源需求编号、唯一主责、输入输出/API schema、依赖、错误/空状态、授权规则、验收用例、工作量估计。PDF/导出等未知项先做有时间上限的 spike，结果包括失败样本与结论，再估实施任务。

Definition of Done：需求和验收满足；代码 Review；契约与生成类型一致；迁移经过真实 PostgreSQL 验证；相应单元/集成/E2E 检查通过；无跨空间访问和历史覆盖；失败/重试可演示；staging 部署并 QA 验收；文档与运行指标更新。任务状态依次为 Backlog → Ready → In Progress → Review → QA → Done，Blocked 显示具体依赖与负责人。

每项大工单拆为 1–3 个工作日左右的可验收子任务；8 SP 项必须在执行前分解。SP 仅是原团队的相对估计，不能直接换算为天或用来证明工期。

## 工单模板与依赖管理

工单必须记录：标题、F/US/AC 编号、负责人、范围、非目标、依赖、API/迁移、设计链接、Given/When/Then、异常/越权/并发测试、估算、验收证据和发布版本。以下示例可直接转入任务系统：

**BE-10 子任务：追加决策修订并保存依据快照。** 依赖 BE-08/09、EN-03；服务端锁决策、校验 expected_revision，写 revision 与依据、更新指针、事件、幂等结果，一次提交。Given 决策 v1；When 两标签页都基于 v1 改理由；Then 一次成功为 v2，一次 409，v1 的标题、原因与原依据不变。QA-07 记录响应、数据库记录与历史页面截图；无权限请求统一 404。

关键路径为：认证空间 → 课题/线索 → PDF 上传/阅读/定位 → 证据 → 假设/决策 → 任务 → 全量导出/恢复验收。前端用契约 Mock 提前开发；禁止把 Mock 示例当作已落库成功。遇到关键路径风险，优先切小验证并更新预测。

## 代码协作与变更控制

建议单仓库、受保护 main、小功能分支和 PR，持续保持 main 可集成；每个 PR 关联工单与验收，至少一名审查者。schema/权限/删除/迁移 PR 要有 TL 审查。发布使用版本 tag 与不可变镜像 digest；未经用户明确要求，本次不创建远程仓库、提交、PR 或上线。

需求变更记录“原因、用户价值、影响的页面/API/表/测试、工期影响、取舍、批准人”。新增需求必须明确进入哪个版本，不能隐性添加到冲刺。每周做演示和风险检查，每迭代两周规划/验收/复盘，必要时每天短同步；会议产物是决定与阻塞处理，不要求为了流程增设大量审批层。
