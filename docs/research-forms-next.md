# 普通研究表单恢复：后续实施记录

2026-10-16，导出恢复验收后继续处理。以下是当前源码审查和待实施步骤，尚未
作为功能通过或已修复的证据。完整 F01–F15 / AC01–AC15 与发布门禁保持不变。

## 当前证据

- research-pages.tsx 创建课题与线索仍使用通用 FormDialog，写入后等待列表刷新，
  再关闭表单或导航；notes.tsx 的新建笔记也采用这一流程。
- common.tsx 的 FormDialog 只有异步 pending，没有同步重复提交守卫；失败后
  没有保存确切 API 路径、正文和请求键。表单字段也未在未知结果阶段固定。
- backend/app/api/research.py 的 project_create、thread_create，以及 workflow.py
  的 note_create 直接调用服务，尚未使用幂等回执。因此仅在前端增加一个 Header
  并不能保证服务端重放原创建结果。

## 下一轮顺序

1. 先用真实 HTTP 提交后丢失响应复现课题/线索/笔记重试是否重复；保留失败报告。
2. 为提供有效幂等键的创建请求增加事务级回执、空间/用户/父对象作用域和正文
   冲突校验。兼容现有不带键的 API 调用需明确记录；前端入口必须使用固定键，
   不把服务端仍允许无键调用解读为所有客户端都具有安全重放保证。
3. 创建交互固定原路径、正文、键和可理解的目标；同步阻止重复点击。创建成功
   与列表/详情刷新分开，未知结果不自动换目标或换键。已知拒绝后修正输入与
   未知结果重放需要不同处理，不为了恢复覆盖历史或绕过版本检查。
4. 验证关闭/重开、父课题/顶栏变化、后页选项、响应延迟、刷新失败、时间守卫，
   以及原对象已被后续编辑后的旧回执。旧创建回执不能把当前缓存降回初始版本。
5. 更新契约和明确兼容边界，执行相应数据库/浏览器/整体回归，再记录源码和报告。

引导、假设/关系与元数据修改、通用按钮、版本冲突比较，以及全部页面/状态的
完整审计继续保留，不能被上述三个创建入口代替。生产平台、容量、完整安全/
可访问性、独立日志新鲜 witness、干净机器 CI、SMTP 与真实用户试用也仍开放。
