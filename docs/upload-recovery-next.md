## 已实现的解析请求恢复

PaperManagement 中每个文件始终挂载 ParseRetry 状态组件。即使后台轮询已从失败
变成排队或成功，未确认请求仍保留原 file/path/key，不能因旧按钮消失而丢失。
写入成功只确认解析请求被接收，不宣称解析完成；后续状态读取独立，不再 POST。
再次失败后，需要先只读核对，再明确发起新任务，才使用新键；未确认阶段不会
提供新任务入口。请求采用现有 30 秒等待与 23 小时重试守卫，不跨页面卸载持久化。

验证使用项目内生成 PDF、测试专用账户和已上传文件。为可重复进入失败分支，
将确切测试文件的 parse_status 改为 failed；随后 HTTP、实际队列和 PDF 解析均
真实执行。这不等于重现一种生产解析器故障。浏览器用例比较丢失回执前后的键/
job_id，读取实际任务数量；两次明确解析意图只新增两个任务，而不是四个。
最终测试结果见进度.md、进展.md 和 implementation-status.md。

## 明日优先：UploadButton 多阶段恢复

当前 library.tsx 的上传初始化和完成仍每次产生新键，文件更换和异常后没有稳定
阶段对象。需要保留选择时的 paper/project、File/摘要，以及各阶段原始请求键：

1. 预检和同摘要文件提示失败可重试，但不能假称上传已开始或自动跳过复用选择。
2. upload-init 同键返回原 upload_id/paper_id/file_id；未知结果不能重新选文件或换键。
3. content 会话为 pending 时可覆盖 staging，因此只能重传同一份字节；先 GET
   /uploads/{id}，validating/completed 时不得再传内容。已传内容的响应丢失不会
   改变 pending 状态，GET pending 不能证明未收到；相同字节重传需验证。
4. upload-complete 保留原 upload_id/键，返回 202 后才显示后台已接收；不要把
   后续列表读取失败当成上传失败。过期/failed/状态读取失败须明确区分。
5. 会话目前一小时过期，普通幂等回执一天。过期旧回执不能被悄悄换成新版本；
   确认需要重新上传时，应作为用户明确的新意图，并说明旧保留记录及额度状态。

queue_upload_validation 当前只查 queued/running/succeeded 的既有任务。若上传已
completed 但解析任务已 failed，新的完成请求可能生成新任务；需要审查它与显式
parse-retry 的边界，避免恢复流程隐式重新解析。此项为代码审查发现，尚未改动。

[导出恢复验收](export-state-acceptance.md)；当前后续工作见

- `frontend/src/components/data-settings.tsx` 每次点击创建都生成新的幂等键，
  没有保存原 include_files/请求键/回执。原任务完成后，列表阻止活跃任务的规则

  已确认接收分开。按钮只有异步 pending 状态，缺少同步重复提交守卫。
- 服务端 `POST /exports` 已有空间锁、活跃任务约束和幂等回执；
  `GET /exports/{id}` 与授权下载入口可用于独立状态核对。

下一轮先建立真实 HTTP/数据库/对象存储回归：提交后丢失回执，再等原任务完成，
核对相同键仍返回原 job，而不是新建档案；覆盖选项改变、连续点击、读失败、
失败/过期档案及授权下载。保留原 include_files 和请求意图，确认任务接收与 ZIP
打包/下载成功分别反馈。此段为待实施审查，不是已修复或通过的证据。

普通研究表单、引导、笔记建档和元数据/关系修改的失败恢复继续保留，不能因
